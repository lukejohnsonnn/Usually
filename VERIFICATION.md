### Matching — how it works now (lib/game.js)

Every submission and every stored variant is canonicalized first: lowercase + NFKD, then a small alias map (cell phone / mobile phone / smartphone → phone, television / telly → tv, refrigerator → fridge, sofa → couch, money → cash, etc.), filler words dropped (my, your, their, of, to, and, ...), then a light stemmer (plurals, -ing/-ed/-ly, irregulars like children → child). Matching is then scored, best per rank:
- exact canonical match (covers exact, case, plural, synonym, word order, filler words): **1.00**
- token-level fuzzy (every token within edit tolerance, Damerau-Levenshtein so a transposition counts as 1): **0.85–0.90**
- whole-string typo fallback (old behavior): **0.80**

A rank wins only at ≥ 0.80 **and** beating the next-best rank by ≥ 0.10. A near-tie means the answer is genuinely ambiguous, so it scores as unlisted (5 pts) rather than guessing wrong. Short tokens (≤3 letters) must match exactly — that is what keeps "cat" from matching "car". Token counts must agree for the fuzzy path, so a subset never matches a longer answer: "phone" does not match "phone screen", "dog" does not match "hot dog", "keys" does not match "keychain".

Tier bands are unchanged: expanded ranks fall into the existing 31+ band (5 pts). No #1 is ever shown on the text reveal (unchanged). No scoring, gameplay, or composition changes.

## 2026-11-16 entry-grid collapse — flex-item width bug (live-site report)

Luke reported the entry grid still never appears on the live answering screen:
no dots before touching the slider, none after dragging to 70% or 96%; the gap
between the big guess number and the slider is only ~108px (a 10x10 grid
needs ~190px); a pixel scan found zero dot pixels, only the legend
"Gold ring = your guess" shows — while the SAME grid component renders 100
dots correctly on the reveal screen. The user and two independent browser
checks confirmed this. Ruled out by the parent: the live-served app.js and
styles.css are byte-identical to origin/main (diff clean, Cache-Control
max-age=0, ETag present) — not a stale deploy or stale cache.

**Root cause (layout, not DOM/JS).** Reproduced in a real DOM with jsdom
(`/tmp/jsdom-repro/repro.mjs`, jsdom 31, real server on a throwaway store):
across a full 7-round Endless play the DOM is perfect — the entry grid
always has 100 children with exactly the right classes (Guess round at 50:
50 gold; slider→70: 70 gold; slider→96: 96 gold; Split round: navy/poppy
halves, zero gold while answering; reveal grids: correct regions), zero JS
errors. The bug is pure layout:

- `index.html` has `<main id="screen">` — the screen element IS the `<main>`,
  and `main` is `display:flex; flex-direction:column`. So `#entry-grid` is a
  **flex item** of a column flex container.
- `.grid.entry` set horizontal auto margins (`margin:10px auto 4px`). A flex
  item with auto cross margins is NOT stretched — per the flexbox spec,
  stretch only applies when neither cross-axis margin is auto — so the
  item's width resolves to its fit-content width.
- The grid's fit-content (max-content) width with `repeat(10, 1fr)` columns
  holding only empty aspect-ratio dots is just the gaps: each `1fr` track's
  intrinsic contribution is the items' max-content size, and empty divs
  contribute 0 — so max-content width ≈ 9 gaps × 3px = 27px.
- In a 27px-wide container the 1fr columns get 0px each (27 − 27 gaps = 0
  free space), and the dots, sized only by `aspect-ratio:1`, become 0×0.
  Grid height = 10 rows × 0 + 9 gaps × 3px = 27px. Predicted gap between
  the big-guess number and the slider: 4 (big-guess margin) + 41 (grid with
  margins) + ~29 (legend) + 10 (controls padding) + 18 (slider margin)
  ≈ 102px — matching the observed ~108px (a working 188px grid would leave
  ~263px). The legend still shows because its height comes from text.
- The reveal grid works only because it sits inside a block `.card`, where
  `width:auto` fills the card and `max-width:188px` caps it at a definite
  188px. Same for the fine-tune grid (`#ft-grid` inside a card).

**Fix (one property, `client/styles.css`).** `.grid.entry` now sets a
definite width: `width:100%; max-width:188px` — the 100% resolves against
the flex container's content width, the max-width caps it at the exact
188px spec, and the auto margins center it. On a screen narrower than
188px of content it shrinks with the screen instead of overflowing. No
gameplay, scoring, question, size, or color change — still the exact Muse
spec (188px, gap 3px, inset gold rings, hollow white guess dots). A CSS
comment on the rule explains the mechanism so it is not reintroduced.
`jsdom` was added as a devDependency (`package.json`) so the regression
check below can run under `npm run verify`.

Root cause: today's frozen daily set `[33,135,113,88,49,128,39]` froze in the morning from the old 119-question bank, and id 39 (a guess-kind finale, "What % of US adults have ever finished a full marathon?", answer 1) was removed in the audit. `POST /api/play` daily called `snapshotFor(ids)`, which did `byId.get(39)` → `undefined` → read `.id` → TypeError, an uncaught async rejection, so the Node process died and Render 502'd every request until it restarted. The parent's live daily POST took 21.6s and returned 502; the very next Endless POST also 502'd until the restart. Endless was immune because `composeSet` draws only from the current bank; `/api/today` was immune because `pub()` filters missing ids (it returned 6 questions). Reproduced locally pre-fix with the throwaway-store harness (`/tmp/usually-bugfix-test.mjs`): same TypeError at server.js:155, process exit code 1.
- **The fix (server.js only).**
  - Daily creation filters the frozen set to bank-present ids before snapshotting, and `questionIds` are derived from the snapshot (`snap.map(s => s.id)`) so the two can never drift apart. The stored frozen set is NOT rewritten — the frozen-set rule stands; only the play built from it is filtered (verified: the stored set still holds all 7 ids incl. 39).
  - `snapshotFor` skips ids missing from the bank (defense in depth).
  - Submit handler reads the note defensively (`byId.get(q.id)?.note || null`), so a pre-deploy play mid-flight can still submit its finale round from its snapshot (answer included) and complete — verified: round-7 submit on a stale play returns 200, Bullseye 175, `completed=true`.
  - New `alignPlay` helper (read paths only: `POST /api/play` existing-play branch, `/api/results`, `/api/contribute`, `/api/share`): an in-progress play whose frozen set lost an id gets its `questionIds`, `snapshot` AND `results` filtered together, score recomputed from the kept results, and `completed=true` if every remaining round is answered. Completed plays are left untouched (history). The submit handler is deliberately NOT aligned — a stale in-memory client must still be able to submit its finale round from the snapshot.
  - `/api/yesterday` also filters its set to bank-present ids.
  - **Process robustness:** every async route handler now runs through `ah()` (a rejection catcher), an error middleware returns 500 JSON (400 for malformed JSON) instead of an uncaught exception, and `unhandledRejection`/`uncaughtException` are logged as a last resort rather than killing the process.
- **ALIGNMENT CONSTRAINT (standing).** The submit handler reads `play.snapshot[roundIndex]` positionally and completes when `results.length >= play.questionIds.length`. `questionIds`, `snapshot`, and `results` must always hold the same ids in the same order — never drop an id from one without the other two. That is why creation derives `questionIds` from the snapshot and why `alignPlay` filters all three together.
- **Verification (local only, throwaway file store, never the live site).** `npm run verify` 148/148.
